# 舞蹈机器人比赛流程与视觉识别通信设计

## 1. 目标与范围

本设计针对现有 ESP32-S3 ESP-IDF 工程，先完成电脑通过 ESP32 SoftAP 获取摄像头画面、进行姿态识别并把识别结果回传给 ESP32 的第一阶段能力，并为后续接入 SU-03T、音乐韵律识别和 Arduino 动作执行预留稳定接口。

本阶段包含：

- 使用现有 ESP32 SoftAP，让电脑连接 `ESP32-Pose` 后访问 `http://192.168.4.1/`。
- 网页显示摄像头画面，承载电脑端姿态识别流程。
- 电脑端将姿态识别结果通过 HTTP 消息回传给 ESP32。
- 建立独立比赛状态机，后续由语音模块、网页姿态识别和串口模块投递事件。

本阶段不包含：

- SU-03T 的语音词条、UART 参数和识别固件。
- ESP32、Arduino、SU-03T 的实际接线、电平转换和硬件保护。
- 通过网页配置比赛项目、阶段顺序或动作键值。
- 通过网页开始、停止、复位或直接控制比赛。
- 具体机器人动作算法、动作完成反馈协议。
- 音乐韵律分类算法。

## 2. 当前工程约束

- 目标芯片为 ESP32-S3。
- `wifi.c` 已实现 SoftAP，默认 SSID 为 `ESP32-Pose`，密码为 `12345678`，AP 地址为 `192.168.4.1`。
- `web.c` 当前在 80 端口提供首页和快照，在 81 端口提供摄像头 MJPEG 流。
- `main.c` 的 PC 视觉模式会启动摄像头、Wi-Fi 和 Web；当前 local pose 模式会停止 PC 模式。
- 现有姿态推理接口能够输出稳定姿态结果，但尚未与比赛流程连接。
- `audio_i2s` 目前提供音频采集/播放接口，但没有音乐识别器。
- 当前 `audio_i2s` 已按 INMP441 采集方式配置：BCLK 为 GPIO 40、WS 为 GPIO 39、DATA 为 GPIO 38，采样率为 16 kHz、采样位宽为 32 bit。
- 赛事规定音乐源文件位于 `D:\robot\舞蹈-表演赛指定音乐`，当前包含 `1.wav` 至 `5.wav` 五个片段；源文件为双声道、16 bit PCM，采样率为 44.1 kHz 或 48 kHz，每段约 15 秒，总大小约 14.05 MB。

比赛流程不能依赖网页请求推进，也不能把比赛控制写进网页处理函数。网页只负责姿态识别和发送姿态识别消息；比赛环节切换必须由机器人自身的语音模块事件驱动。

## 3. 总体架构

```text
电脑 ──Wi-Fi──> Web/姿态识别页面 ──HTTP姿态消息──> ESP32 web.c
                                                        │
SU-03T 事件适配器 ──────────────────────────────────────┤
音乐识别事件适配器 ─────────────────────────────────────┤
Arduino 动作反馈适配器 ─────────────────────────────────┘
                                                        │
                                      competition_controller
                                          │          │
                                          │          └── 状态/日志/LED
                                          └── action_sender
```

模块边界：

- `competition_controller`：唯一拥有比赛状态、计时器和阶段推进逻辑的模块。
- `web`：展示摄像头画面、接收姿态识别消息；不读写比赛配置、不切换阶段、不直接发送动作键值。
- `serial_bridge`/动作发送器：将控制器批准的动作转换为 Arduino 串口发送；具体协议另行实现。
- 识别适配器：把 SU-03T、网页姿态识别、音乐模块的结果转换为统一事件，不关心比赛阶段细节。
- `music_recognizer`：从 INMP441 的 I2S 音频采样中提取节拍/韵律特征，在音乐阶段产生音乐识别事件；不负责选择比赛阶段。

音乐数据流：

```text
场外音乐播放设备
        ↓ 空气声
      INMP441
        ↓ I2S
    audio_i2s
        ↓ PCM采样
music_recognizer
        ↓ 韵律识别事件
 competition_controller
```

规定音乐识别库的处理方式：

- `1.wav` 至 `5.wav` 只作为离线预处理输入，不直接作为完整 WAV 文件编入固件。
- 离线工具统一执行双声道转单声道、重采样到 16 kHz、幅度归一化，并提取节拍/频谱指纹。
- ESP32 固件只携带五组紧凑特征，运行时将 INMP441 的采样窗口与特征库比较，输出音乐编号 `1`–`5` 和置信度。
- 识别器必须保留“未识别”结果，置信度不足时不能误报规定音乐编号。

## 4. 比赛事件模型

比赛环节的实际顺序由语音模块在比赛过程中指定，不固定为“语音、视觉、音乐”。阶段命令、项目选择和动作映射由语音模块协议/固件或后续独立配置模块提供，不由网页修改。

### 4.1 阶段事件

语音模块协议至少需要能够表达三个阶段：

- `VOICE`：语音识别-动作表演。
- `VISION`：视觉识别-动作表演。
- `MUSIC`：音乐韵律识别-动作表演。

控制器收到阶段事件后必须检查：

- 当前处于等待阶段命令状态，而不是另一个阶段正在运行。
- 该阶段尚未完成，不能重复进入。
- 事件编号属于语音模块协议定义的合法阶段事件。

非法或重复阶段事件只记录日志，不得触发动作。

### 4.2 识别和动作事件

语音模块、网页姿态识别和音乐模块统一转换为事件：

- 识别类型：语音、视觉或音乐。
- 识别编号。
- 置信度（如适用）。
- 产生时间或序号。

控制器只在当前阶段、当前项目匹配时接受识别事件。网页回传的姿态识别消息只能产生视觉识别事件，不能指定动作键值。

## 5. 状态机

```text
IDLE
  └─(语音模块准备/开始事件)──> READY_FOR_STAGE
                                  └─(语音模块阶段事件)──> RUNNING_STAGE
                                                        ├─ WAIT_RECOGNITION
                                                        ├─ DISPATCH_ACTION
                                                        ├─ WAIT_ACTION_DONE
                                                        ├─ MUSIC_RECOGNITION
                                                        ├─ MUSIC_PERFORMANCE
                                                        ├─ STAGE_COMPLETE
                                                        ├─ READY_FOR_STAGE
                                                        ├─ COMPLETE
                                                        └─ ABORTED / FAULT
```

### 5.1 等待和运行

- 控制器启动后等待语音模块的准备/开始事件。
- 准备事件锁定本次比赛所需的项目快照，但不选择具体比赛环节。
- `READY_FOR_STAGE` 只接受语音模块发送的阶段事件；网页不能切换阶段。
- 比赛使用单调时钟记录总比赛时间、当前阶段时间和当前项目时间。
- 总比赛计时上限为 15 分钟；语音、视觉、音乐阶段各自上限为 5 分钟。
- 一个阶段完成后回到 `READY_FOR_STAGE`，等待语音模块指定下一个阶段。
- 三个不同阶段都完成后进入 `COMPLETE`；重复指定已完成阶段时拒绝。

### 5.2 语音/视觉环节

每个项目按语音模块给出的项目顺序执行：

```text
WAIT_RECOGNITION
  ├─ 收到匹配识别事件 ──> DISPATCH_ACTION
  ├─ 收到失败/超时 ─────> FAILED 或等待重试
  └─ 收到后续项目事件 ──> 忽略并记录

DISPATCH_ACTION
  └─ 动作发送成功 ──────> WAIT_ACTION_DONE

WAIT_ACTION_DONE
  ├─ 收到动作完成 ──────> 下一个项目
  └─ 达到动作超时 ──────> FAILED 或下一个项目
```

当前 Arduino 没有动作完成反馈时，可先采用“发送成功即派发完成”的实验模式；正式比赛前应替换为真实反馈或经过验证的动作时长模型。

### 5.3 音乐环节

每段音乐严格按两个阶段执行：

```text
MUSIC_RECOGNITION
  └─ 韵律识别完成 ──> MUSIC_PERFORMANCE

MUSIC_PERFORMANCE
  ├─ 达到合法表演时长 ──> 下一段音乐
  ├─ 超过项目上限 ──────> 自动结束并记录超时
  └─ 阶段达到 5 分钟 ────> 阶段结束
```

不能跳过音乐识别阶段直接表演。规定音乐表演时长固定校验为 60–90 秒，自选音乐为 90–120 秒；音乐播放设备由比赛现场负责，ESP32 只接收识别、开始表演和结束表演事件。

音乐识别阶段使用 INMP441 采集比赛现场播放的音乐。`music_recognizer` 只在控制器进入 `MUSIC_RECOGNITION` 后运行，在识别成功或超时后停止/切换到表演状态；非音乐阶段不应将音频采样解释为比赛事件。

规定音乐识别时，识别器使用上述五个离线生成的特征库进行匹配。由于原始片段采样率不同，所有比较必须在统一的 16 kHz 单声道特征空间中完成；不得直接按 WAV 文件字节比较。

## 6. ESP32 双串口通信设计

### 6.1 UART 分工

UART0 保留给 ESP-IDF 日志和 USB 调试，不参与设备通信。新增两条硬件 UART：

| ESP32 UART | 对端 | 方向 | 用途 |
|---|---|---|---|
| UART1 | SU-03T UART1 | 双向 | 接收 SU-03T 的语音/阶段/音乐命令；回传识别结果和状态消息 |
| UART2 | Arduino `mySerial2` | 双向预留 | ESP32 向 Arduino 发送动作键值；预留接收 Arduino/机器人反馈 |

两条设备 UART 默认均为 `115200, 8N1`，不自动添加校验字节。ESP-IDF 中使用硬件 UART 驱动和 RX 队列，不使用 `SoftwareSerial`。

当前工程已占用的 GPIO 包括摄像头 GPIO4–18、音频 GPIO38–40、LCD GPIO14/15/41/42/47 和 BOOT GPIO0。可先采用以下软件默认候选，最终仍以开发板实际引脚复核为准：

```text
UART1 / SU-03T: RX GPIO1,  TX GPIO2
UART2 / Arduino: RX GPIO20, TX GPIO21
```

其中 UART2 的核心发送方向是 `ESP32 TX GPIO21 -> Arduino mySerial2 RX(GPIO12)`；Arduino 的 `mySerial2 TX(GPIO13)` 接入 ESP32 UART2 RX 仅作为反馈预留，当前给出的 Arduino 程序没有向 `mySerial2` 写回数据。

### 6.2 SU-03T 到 ESP32

SU-03T 的 `UART1_TX` 进入 ESP32 的 `UART1_RX`。ESP32 逐字节接收并记录十六进制、十进制和接收时间，然后交给协议适配器：

```text
SU-03T UART1_TX
        ↓
ESP32 UART1_RX
        ↓ 原始字节日志 / 协议适配
stage_command / voice_recognized / music_command
```

从截图可确认的 SU-03T 配置语义如下，ESP32 先按原始字节接收，语义映射放在协议适配器中：

| SU-03T 行为 | 页面中显示的参数/消息 | ESP32 处理方向 |
|---|---|---|
| `Forward`、`LFoot`、`LHand`、`TurnL`、`TurnR`、`jiebei`、`fangyu`、`chuquan` | UART1_TX 参数 `01`–`08` | 识别为动作候选，再转换/转发到 Arduino |
| `task1`、`task2`、`task3` | UART1_TX 参数 `AA`、`BB`、`CC` | 交给比赛状态机切换语音、视觉、音乐阶段 |
| `lear_eyes`、`lear_music` | UART1_TX 参数 `11`、`22` | 分别作为任务二、任务三的语音引导入口 |
| `one`、`three`、`four`、`five` | UART1_TX 参数 `11`、`33`、`44`、`55` | 交给音乐编号识别逻辑 |
| `music`、`my_music` | UART1_TX 参数 `55`、`66` | 交给正式/自选音乐表演阶段逻辑 |
| `two` | UART1_RX 消息 `7` | 作为 SU-03T 回传提示的协议样本 |

以上参数以用户提供的 SU-03T 配置表为准；调试阶段仍应记录真实 UART 抓包，确认模块实际发送的是单字节十六进制值，而不是两个 ASCII 字符。

SU-03T 页面显示的 `01`、`02` 等参数必须以实际抓到的 UART 字节为准。Arduino 程序比较的是 ASCII 字节，例如 `cmd == 49` 实际表示 ASCII `'1'`（`0x31`），不是数值字节 `0x01`。因此第一版桥接必须保留原始字节，不擅自把 `0x01` 转成 `'1'` 或反向转换。

### 6.3 ESP32 到 Arduino

Arduino 的 `mySerial2(12, 13)` 中，GPIO12 是 RX、GPIO13 是 TX。ESP32 不改变 Arduino 的现有映射逻辑：

```text
SU-03T/视觉/音乐事件
        ↓
ESP32 动作协议适配器
        ↓ 一个动作命令字节
ESP32 UART2_TX
        ↓
Arduino mySerial2_RX(GPIO12)
        ↓
Arduino 原有 cmd 映射
        ↓
Arduino mySerial1.println(...)
```

向 Arduino 发送动作命令时必须发送单个原始命令字节，不追加 `\\r`、`\\n`。Arduino 原程序会自行通过 `mySerial1.println()` 向机器人控制器发送动作字符和行结束符。

### 6.4 当前 Arduino 命令映射

根据给出的代码，Arduino 实际识别 21 个输入字节，而不是 20 个：

| 输入字节 | ASCII | Arduino 转发内容 |
|---:|:---:|:---:|
| `0x31` | `1` | `7` |
| `0x33` | `3` | `4` |
| `0x32` | `2` | `6` |
| `0x34` | `4` | `5` |
| `0x39` | `9` | `D` |
| `0x61` | `a` | `B` |
| `0x62` | `b` | `A` |
| `0x63` | `c` | `C` |
| `0x42` | `B` | `K` |
| `0x43` | `C` | `8` |
| `0x46` | `F` | `J` |
| `0x66` | `f` | `E` |
| `0x64` | `d` | `H` |
| `0x65` | `e` | `F` |
| `0x41` | `A` | `G` |
| `0x35` | `5` | `3` |
| `0x37` | `7` | `1` |
| `0x36` | `6` | `2` |
| `0x38` | `8` | `10` |
| `0x44` | `D` | `L` |
| `0x45` | `E` | `9` |

这里的 `mySerial1.println(10)` 会发送文本 `10\\r\\n`，不是单个 `0x0A` 字节；ESP32 侧不应替 Arduino 改写这一行为。

### 6.5 ESP32 回传 SU-03T

ESP32 UART1_TX 向 SU-03T `UART1_RX` 回传消息，供 SU-03T 的“串口输入”触发播报或状态提示。根据截图，UART1_RX 的消息编号使用固定 5 字节帧：

```text
AA 55 <message_id> 55 AA
```

例如消息编号 4 的测试消息为：

```text
AA 55 04 55 AA
```

因此 ESP32 发送消息编号 1–14 时必须发送完整帧，不能只发送消息编号，也不能追加 `\\r` 或 `\\n`。帧解析器应按 `AA 55` 帧头同步，读取一个消息编号，并要求紧接着收到 `55 AA` 帧尾；帧错误时丢弃当前帧并重新寻找下一个帧头。

视觉消息编号 `1`–`6` 分别关联大字站、举手、蹲下、弓步、叉腰、敬礼；音乐编号 `1`–`5` 对应 SU-03T 消息 `10`–`14`。例如音乐三识别成功时发送消息 `12`，即 `AA 55 0C 55 AA`。ESP32 视觉识别结果和音乐编号均通过同一条 SU-03T TX 通道使用上述帧格式回传。

### 6.6 通信任务和错误处理

- 每条 UART 使用独立 RX 任务和发送互斥锁，避免视觉/音乐任务同时写串口造成字节交错。
- RX 任务只负责收包和投递事件，不在 UART 回调中执行动作或模型推理。
- 未知字节保留日志；是否转发给 Arduino 由桥接策略决定，默认只转发命令表中的动作字节。
- UART 缓冲区溢出、发送超时和无效阶段命令进入错误日志，不复位比赛状态机。
- 调试阶段提供“原始字节透传/日志模式”和“SU-03T 帧收发日志”；正式比赛默认关闭大批量十六进制日志，避免影响实时性。

## 7. 网页与 HTTP API

网页只负责姿态识别和回传姿态识别消息，不负责比赛配置或比赛控制。

保留现有接口：

- `GET /`：姿态识别页面和摄像头入口，不显示比赛控制按钮。
- `GET /snapshot`：现有快照接口。
- `GET /stream`（端口 81）：现有视频流。

新增接口：

- `POST /api/vision/pose`：电脑端网页提交姿态识别结果给 ESP32。

姿态消息至少包含：

- `pose_id`：姿态编号。
- `confidence`：识别置信度。
- `timestamp`：电脑端识别时间或序号。

ESP32 收到后只执行格式、置信度和当前比赛状态校验，然后调用 `competition_on_visual_recognized()`。姿态消息不能直接指定动作、切换阶段或复位比赛。

响应至少包含：

- `ok`：请求是否成功。
- `accepted`：当前阶段是否接受该姿态事件。
- `error`：失败时的机器可读错误码。
- `state`：当前比赛状态。

非视觉阶段收到姿态消息时返回 `accepted=false`，只记录日志，不触发动作。网页第一版使用 `web.c` 内嵌 HTML/CSS/JavaScript，避免引入新的前端构建链。

## 8. 自主运行与安全边界

- 网页不提供比赛配置、阶段选择、动作键值、开始、停止或复位控件。
- 网页回传的姿态消息只能作为视觉识别事件，不能绕过当前阶段直接控制机器人。
- 姿态识别页面刷新或重复上报不会绕过当前状态机，也不会直接触发动作。
- Wi-Fi 断开不暂停、不重置比赛；状态机继续运行。
- HTTP 请求超时、格式错误或重复请求不能破坏比赛状态。
- 比赛异常由内部状态转为 `FAULT`/`ABORTED`，记录原因并停止后续动作派发。
- 实验模式必须与比赛模式显式区分，避免调试用远程控制进入正式比赛。

## 9. 第一阶段验收标准

1. ESP32 启动后日志显示 SoftAP 已启动，电脑可连接 `ESP32-Pose`。
2. 浏览器访问 `http://192.168.4.1/` 能显示摄像头和姿态识别页面。
3. 电脑端姿态识别结果能通过 `POST /api/vision/pose` 回传给 ESP32。
4. ESP32 能返回消息是否被当前比赛状态接受，非视觉阶段不会触发动作。
5. 模拟语音模块发送合法阶段事件后，状态切换到对应阶段；网页不能直接切换阶段。
6. 视觉阶段收到合法姿态消息后，控制器能产生视觉识别事件。
7. 音乐阶段能启动 INMP441 采集任务，并为韵律识别器提供连续 PCM 数据。
8. 离线预处理能为 `1.wav`–`5.wav` 生成五组统一格式的紧凑特征，并能还原对应的音乐编号。
9. UART1 能记录 SU-03T 的原始字节，UART2 能将已确认的动作命令单字节发送到 Arduino。
10. ESP32 发送消息编号 4 时，UART1_TX 实际输出 `AA 55 04 55 AA`，且不追加换行。
11. 帧头、消息编号或帧尾错误时，SU-03T 帧解析器能丢弃错误帧并重新同步。
12. 现有 `http://192.168.4.1:81/stream` 摄像头流仍可用。
13. 工程能通过 ESP-IDF 构建，且不覆盖当前工作区已有的未提交修改。
